PHASE 13 - ENGINE PARITY: UNIFIED SINGLE-SCENE ARCHITECTURE FOR ALL SOLO MODES

SOURCE OF TRUTH: colyseus-babylon-client.js — the working multiplayer engine.
PROBLEM: Solo modes (Quick Race, Time Trial, Grand Prix, Free Roam, Solo Battle) use a broken
  two-scene split architecture: havok-physics.js runs a headless NullEngine for physics,
  babylon-renderer.js runs a separate Engine for rendering. The kart physics body lives in one
  Babylon.js scene, the visual mesh lives in another, and a manual transform relay bridges them.
  The working multiplayer engine (colyseus-babylon-client.js) uses a SINGLE scene where physics
  and rendering coexist — Havok steps automatically inside scene.render(), the kart's visual
  mesh IS its physics body, track colliders live alongside their rendered geometry, and items use
  native Havok trigger shapes. The solo engine must be redesigned to match.
GOAL: All solo game modes use the same single-scene unified physics architecture as multiplayer,
  with identical driving feel, camera behavior, item physics, and track collider fidelity.
AFFECTED MODES: Quick Race, Time Trial, Grand Prix, Free Roam, Solo Battle (5 modes).
UNAFFECTED MODES: Online Race, Online Battle (already working via colyseus-babylon-client.js).

  Mitigation: Execute in strict order. Each sub-phase produces a testable checkpoint. kart-physics.js extraction (13.1) is zero-risk.
- Regression risk to multiplayer: colyseus-babylon-client.js applyLocalPrediction refactored to use shared module.
  Mitigation: Shared module uses identical constants and logic. Run multiplayer regression test after 13.1.2.
- Track collider alignment: Current pattern extracts geometry and transforms manually. New pattern clones meshes with bakeCurrentTransformIntoVertices.
  Mitigation: Exact same pattern proven working in multiplayer. Test on cocoa_temple (complex geometry) early.
- Bot physics: Bots currently use kinematic positioning. May need ANIMATED physics bodies in unified scene.
  Mitigation: Start with kinematic (no physics body). Add ANIMATED bodies only if collision detection requires it.
- Custom track builder: buildCustomTrackScene() creates box meshes with createBoxCollider() from havok-physics.js.
  Mitigation: Replace with PhysicsAggregate(box, BOX, {mass:0}, scene) directly in the rendering scene. Small change.
- Performance: Single scene now runs both rendering AND physics. NullEngine had zero rendering cost.
  Mitigation: Multiplayer already uses this pattern at 60fps with no issues. STK tracks render fine. Not a concern.

POTENTIAL CHALLENGES AND MITIGATIONS
- C++ to WASM compilation: stk-editor uses GTK, IRrlicht, and filesystem APIs that don't exist in browser.
  Mitigation: Strip all GUI/rendering — WASM only handles geometry math and export logic. JS handles all UI/rendering.
- WASM module size: Full editor could be large.
  Mitigation: Extract only road geometry + export code. Target <2MB gzipped. Lazy-load only on builder page.
- Track data sync latency in multiplayer: Large tracks could slow room joins.
  Mitigation: Cap track JSON at 64KB. Compress with pako before Colyseus transmission. Validate server-side.
- Physics on custom geometry: Procedural tracks need valid colliders.
  Mitigation: Use simple box/trimesh colliders per segment. Validate no overlapping or missing colliders in validateTrack().
- Browser file I/O: No native filesystem.
  Mitigation: All data via JSON strings in memory. localStorage for persistence. Share codes via clipboard.
- GPL v3 compliance: stk-editor and STK assets are GPL.
  Mitigation: All derived code must carry GPL v3 headers. Track Builder module must be open-source. Document in LICENSE file.

  tune, extend, and polish what exists.
